# v0.2.42 Stable Hash V4 and Build Traceability

## Stable Hash V4

Stable Hash V4 separates Jira data into stable content, volatile metrics, and transport metadata. Only stable content participates in the current content revision.

The volatile-field registry is resolved once for a new database from Jira field metadata. Runtime exclusion uses exact Field IDs only. It does not use substring or regular-expression matching for words such as `Time` or `Duration`.

Confirmed mappings:

- `customfield_12201`: Actual Duration
- `customfield_12401`: Review Time

Other configured names are resolved only when exactly one Jira field metadata entry has the same normalized display name. Missing and ambiguous mappings remain in stable content and produce diagnostics.

Each resolved registry entry records its Field ID, display and normalized names, classification, exclusion reason, resolver source, schema summary, and metadata fingerprint. The policy fingerprint uses semantic registry identity and does not drift for cosmetic display-name formatting.

## Current Observed Metrics

A metric-only refetch has decision `Existing`. It updates `current_observed_metrics` and the successful observation metadata, but it does not:

- increment `content_revision`;
- rewrite the Current Snapshot or compressed Current Payload;
- replace the stable hash;
- create a synthetic activity event.

Numeric Jira metric fields normalize equivalent number strings and JSON numbers before comparison.

## Candidate Diagnostics

When an unregistered field changes while Jira `updated`, changelog, and comments remain unchanged, the app records a candidate without changing policy:

- `volatile-field-candidates.json`
- `stable-hash-field-diff.json`

Candidate value evidence contains only type, length, SHA-256, and a short scalar preview. Full descriptions, comments, authorization data, and tokens are not included.

## Database Compatibility

Current-State schema remains version 2 and Event Identity remains V2. Stable Hash V3 and older databases are read-only in v0.2.42. The app does not migrate or rewrite them; create a new v0.2.42 database for V4 writes.

## Build Traceability

Renderer, Electron main, Full Fetch Result Index, Issue Manifest, Source Object Index, and Source Archive manifest receive one injected build identity:

- application version;
- packaged source commit;
- build time.

Packaging requires a clean tracked worktree and rebuilds from the exact current commit before Electron Builder runs. `release/build-info.json` records the same embedded values for short metadata verification.
