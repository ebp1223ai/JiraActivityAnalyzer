## Baseline reproduction

The supplied v0.3.10 analyzed JSON contains 117 selected records, 117 App requests, 117 request trace identities, 1,415,735 total tokens, and 284 candidates. Of those candidates, 173 (60.9%) are the first Catalog Skill in their Group and 176 (62.0%) end in `_001`. The supplied manual POC marks 38 records EXCLUDED; 21 of those had candidates in the prior software output. These measurements establish the per-record and fallback correctness gap.

The supplied Pending JSON contains 117 eligible records. Its deterministic compact payload is 360,974 bytes, a 64.66% reduction from the 1,021,410-byte source. The complete prompt is 407,037 bytes and conservatively estimates 135,679 input tokens. With 74,880 reserved output tokens and a 16,000-token safety margin, the verified 200,000-token context requires 226,559 tokens and therefore fails before thread creation.

## Single-run contract

For ChatGPT mode, one analysis run creates one compact payload, one App Server `runAnalysis` call, one ephemeral read-only thread, and one turn. Rules and all selected records occur once in the main prompt. There is no per-record loop, application retry, repair turn, batch split, or partial fallback. Provider events are scoped by the analysis run ID plus returned thread/turn identities; stale events cannot mutate another run.

Before any thread is created, Electron re-reads and re-hashes the Pending Dataset and all Manifest-bound rule files. Selected `sourceRecordStableId`, `activityEventId`, `evidenceId`, and `sourceContentHash` values must all be present and unique. The capacity gate uses only the selected model's verified App Server configuration metadata.

## Result correctness

The structured response must contain exactly one record per compact input in source order. Identity fields must match byte-for-byte. MATCHED requires at least one exact Catalog Skill ID; EXCLUDED and UNKNOWN cannot contain candidates. Skill Name and Group are populated locally from the Catalog and cannot be overridden by provider output. Every record and candidate carries negative checks, and candidates retain positive evidence and rejected near-Skill reasons.

Distribution diagnostics are derived locally after validation: candidate count, distinct Skill count, per-Skill and per-Group counts, Group-first candidate count, and `_001` suffix count. They are evidence, not acceptance shortcuts.

## Audit artifacts and persistence

Run-scoped staging contains the deterministic compact payload, capacity preflight, and gzip-compressed final visible provider response with read-back SHA-256 verification. Completed analyzed JSON stores App/build/runtime metadata, prompt version/hash, source/rules identities, capacity values, request/thread/turn counts, usage, distribution diagnostics, and output artifact paths/hashes.

The Golden HTML renderer is shared by ChatGPT, AI Nexus, Offline Rule, and imported legacy runs. It is self-contained, CSP-restricted, escaped, offline, printable, and includes summary metrics, rules snapshot, Skill ranking, Actor/Issue/Skill Group/status/review filters, expand/collapse, original Diff evidence, positive/negative evidence, near-Skill rejection, and explicit Unavailable values for missing legacy fields.

Final JSON and HTML are written and read-back validated before the completed run is committed to the separate AI Analysis SQLite database. Failure removes final artifacts and leaves run-scoped failed staging; failed, cancelled, partial, interrupted, or unknown outcomes never enter completed results.

## Compatibility

AI Nexus keeps its existing provider request behavior but uses the same final schema, distribution diagnostics, persistence gate, and renderer. Offline Rule remains deterministic and network-free. Legacy v0.3.9/v0.3.10 analyzed files are adapted with an explicit warning and display absent v0.3.11 evidence as Unavailable. ENV format remains v4, the source Jira SQLite schema is unchanged, and no direct OpenAI API credential path is introduced.

## Known limitation

The supplied 117-record request cannot be sent safely to a verified 200k-context model with the configured full-output reserve. The product reports `ANALYSIS_INPUT_CONTEXT_TOO_LARGE` before opening a provider thread. A real full run requires a model whose verified context is at least the measured requirement, or an explicitly approved future contract change; this version does not silently batch or omit records.
