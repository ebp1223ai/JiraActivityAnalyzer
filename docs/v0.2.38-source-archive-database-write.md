# v0.2.38 Source Archive Database Write Correctness

## Runtime Flow

User Analysis Stage 5 follows this trusted path:

```text
Save Full Fetch Result
-> typed preload IPC (runId only)
-> Electron main validates the current frozen run
-> save Full Fetch JSON
-> resolve LOCAL_DATABASE_PATH from APP_ROOT/.env
-> verify file-backed eligible canonical files
-> verify current Jira identity against frozen run provenance
-> Source Archive database preflight and Jira binding check
-> per-Issue savepoint write
-> gzip/JSON/SHA-256/Import Ref/foreign-key readback
-> return separate file and database summaries to renderer
```

The renderer never opens SQLite and never receives the full raw dataset. Each eligible Issue payload is loaded from its verified staging files only while that Issue is being stored.

## Database Contract

Schema version remains `1`; v0.2.38 reuses all seven v0.2.37 tables:

- `database_metadata`
- `schema_migrations`
- `source_system_bindings`
- `source_objects`
- `source_object_versions`
- `source_payloads`
- `source_import_refs`

One SQLite database binds to one verified Jira server and can contain multiple Jira projects. The first binding and business writes share an outer transaction. If every eligible Issue fails, the first binding is rolled back. An existing mismatched binding rejects the whole batch with zero writes.

Object identity is `jira + issue + normalized Issue Key`. Jira `source_version_number` is always `NULL`. The payload is deterministic canonical JSON encoded as UTF-8, hashed before compression, then gzip-compressed into a BLOB. Identical content reuses the existing version and payload; changed source content creates a new immutable snapshot.

## Eligibility

Formal database writes accept only `eligible` Full Fetch targets whose required canonical files pass hash, size, and JSON/NDJSON checks. Partial, required-partial, failed, not-attempted, cancelled, in-progress, excluded, invalid-key, stale-run, and unknown-provenance records never create Object, Version, Payload, or Import Ref rows.

The main reason codes are:

- `DATABASE_WRITE_SUCCESS`
- `DATABASE_WRITE_PARTIAL_SUCCESS`
- `DATABASE_NOT_READY`
- `DATABASE_PATH_MISSING`
- `DATABASE_PERMISSION_DENIED`
- `DATABASE_BUSY`
- `DATABASE_CORRUPTED`
- `SOURCE_SERVER_IDENTITY_MISSING`
- `SOURCE_SERVER_MISMATCH`
- `SOURCE_ARCHIVE_UNSAFE`
- `FULL_FETCH_RESULT_STALE`
- `ISSUE_PARTIAL_EXCLUDED`
- `ISSUE_FAILED_EXCLUDED`
- `ISSUE_KEY_INVALID`
- `RAW_PAYLOAD_MISSING`
- `DUPLICATE_EXISTING`
- `DATABASE_WRITE_FAILED`
- `TRANSACTION_ROLLED_BACK`

Debug evidence records safe paths, IDs, counts, reason codes, transaction results, retry counts, and readback status. It does not record tokens, Authorization headers, gzip BLOBs, complete raw JSON, comments, descriptions, or changelog bodies.

## Read-Only Audit

Close the application or ensure no write is active, then run:

```powershell
node scripts/audit-source-archive-database.cjs "D:\path\to\source-archive.sqlite"
```

The utility opens SQLite read-only, reports all seven table counts, runs `PRAGMA integrity_check` and `PRAGMA foreign_key_check`, and verifies every gzip payload size, JSON parse, and SHA-256 hash. It does not modify the database.

## Manual Test Checklist

1. Create a new database in Connections and confirm `.env` contains its `LOCAL_DATABASE_PATH`.
2. Run a synthetic or authorized small Full Fetch with 2-3 complete Issues, then click `Save Full Fetch Result`.
3. Confirm File Save and Database Write are separate, Database Write is `completed`, New Objects/Versions/Payloads match the eligible count, and readback/FK checks pass.
4. Run the read-only audit command and confirm `integrityCheck=ok`, `foreignKeyViolations=0`, and `verifiedPayloads=source_payloads`.
5. Save the same completed run again. Objects, Versions, Payloads, and identical Import Refs must not increase; Existing/Duplicate must increase.
6. Re-fetch one changed Issue and save. Objects must stay constant while Versions and Payloads each increase by one; both old and new payloads must audit successfully.
7. Confirm Partial, Failed, and invalid Issue keys do not appear in any of the four formal Issue tables.
8. Select a database bound to another Jira server. The batch must fail with `SOURCE_SERVER_MISMATCH` and all counts/seen times must remain unchanged.
9. Restart Installer and Portable builds. Confirm they resolve the same database path beside `APP_ROOT` rules and do not create a fallback under `%LOCALAPPDATA%`.

v0.2.38 does not import historical JSON/ZIP/staging manually, merge databases, create `activity_events`, split evidence into new tables, migrate schemas, or repair databases.
