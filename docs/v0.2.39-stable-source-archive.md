# v0.2.39 Stable Source Archive

## Scope

Version 0.2.39 makes repeated Jira Full Fetch saves produce meaningful immutable snapshots and queryable activity events. It does not add Database Merge, external SQLite dependencies, or destructive cleanup of legacy versions.

## Stable Projection

`buildStableSourceProjection` is the single production implementation used by new writes, migration backfill, diagnostics, and tests. It retains Jira issue fields, changelog, comments, attachment metadata, users, issue links, remote links, and normalized current fields.

The projection excludes:

- `evidence`, because it depends on selected user and analysis conditions.
- `normalizedCurrentFields.fetchedAt`, because it is acquisition time.

The volatile registry narrowly normalizes `issue.fields.customfield_10900` values matching a fully qualified Java class followed by `@` and a hexadecimal object identity. Ordinary email addresses, Jira keys, URLs, and all unregistered custom fields remain meaningful.

Arrays with stable source identities are canonicalized deterministically. Changelog item order is preserved because item order can be semantically meaningful.

## Hash Semantics

`content_hash` remains the archive payload SHA-256:

```text
SHA-256(complete canonical payload UTF-8 bytes)
```

It validates gzip readback and exact stored payload integrity.

`stable_version_hash` is:

```text
SHA-256(canonical Stable Source Projection)
```

It controls snapshot identity. An equal stable hash is `duplicate`; the existing Object and Version seen timestamps are updated, while no Version, Payload, Import Ref, or Activity Event is inserted. A changed stable hash must produce at least one meaningful changed path before a new Version is accepted.

## Schema v2

Schema v2 adds:

- `source_object_versions.stable_version_hash`
- `source_object_versions.version_identity_status`
- `source_system_bindings.connection_label`
- `source_system_bindings.server_title_status`
- `activity_events` and supporting indexes

New versions are `stable_verified`. Migrated versions are `legacy_unverified`; duplicate legacy groups are reported but never deleted or collapsed.

## Migration

Migration preflight verifies the SQLite header, schema v1, `quick_check`, and foreign keys. A collision-safe `VACUUM INTO` backup is created beside the database and validated as schema v1 before migration begins.

Schema changes, stable-hash backfill, and activity-event backfill run in one transaction. Each legacy payload is decompressed and checked against its existing archive hash. The compressed payload bytes are not rewritten. Any schema, payload, event, or injected failure rolls back the original database to schema v1; the validated backup remains available.

Running migration again against schema v2 is a no-op.

## Activity Events

The event projection supports:

- `issue_created`
- `field_changed`
- `status_changed`
- `assignee_changed`
- `comment_created`
- `comment_updated`
- `attachment_added`
- `issue_link_changed`

Event hashes are deterministic across repeated snapshots. Existing events are ignored by hash, allowing changed snapshots to add only newly observed activity.

## Server Identity

`connection_label` is the user-facing connection name. `server_title` is populated only from a successful Jira `/serverInfo` response and carries a verified/unverified status. Offline migration moves the old ambiguous title into `connection_label` and leaves the official title unverified until Jira connection succeeds.

## Diagnostics

Debug Folder includes:

```text
source-archive-migration.json
source-version-projection/
  <ISSUE>-stable-projection.json
  <ISSUE>-hash-input.json
  <ISSUE>-version-decision.json
```

Normal renderer IPC results keep raw projection bodies out of the result summary.

## Deferred

Database Merge and destructive cleanup or consolidation of legacy duplicate versions are deferred to v0.2.40.
