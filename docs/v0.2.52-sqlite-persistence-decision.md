# v0.2.52 SQLite Persistence Decision Note

## Current decision

Runtime/UI semantics are implemented. Persistent SQLite schema and historical migration remain pending user decision. `CURRENT_STATE_SCHEMA_VERSION` stays at `2`; v0.2.52 does not recreate, migrate, or mutate an existing database schema.

## Options considered

| Option | Description | Data trust | Existing DB impact | Rollback | Viewer/Export/Debug impact | Performance | Recommendation |
|---|---|---|---|---|---|---|---|
| A | Keep schema v2 and compute availability/diff at read time | Correct for source-presence evidence currently available; historical ambiguity remains explicit | None | Immediate | Shared runtime normalizer required everywhere | Bounded CPU/cache cost | **Selected for v0.2.52** |
| B | Add availability/canonical/diff columns to `activity_events` | Strong per-row semantics | Migration and backfill required | Requires down migration/backup | Simplest reads after migration | Larger rows and write cost | Defer |
| C | Add sidecar `activity_event_semantics` table | Strong versioned semantics without widening event rows | Migration required; old rows can remain unavailable until backfill | Drop sidecar after verified rollback | Join required; best provenance/versioning | Index decision required | Preferred future candidate |
| D | Recreate or rewrite historical databases | Can normalize all rows if raw evidence is complete | Highest risk; violates current preservation requirement | Restore-only | Broad artifact and compatibility change | Long migration | Rejected for automatic use |

## Questions requiring user decision

1. Should availability, canonical text, `diffStatus`, and `diffBasis` become persisted facts or remain derived runtime semantics?
2. If persisted, should the design widen `activity_events` or use a versioned sidecar table?
3. Must historical databases be backfilled transactionally, or may old rows remain explicitly `unavailable`?
4. Is a verified backup/hash manifest mandatory before migration?
5. Should after-only fallback be persisted as `diffBasis=after_only`, or recalculated by the current normalizer version?
6. What rollback and portable/installer containment evidence is required before enabling migration?
7. Should the app refuse formal writes until the user explicitly accepts the migration plan?

## Recommendation

Keep schema v2 for v0.2.52. If persistence is approved later, prototype Option C with a transaction, compatibility preflight, backup/hash manifest, rollback rehearsal, query benchmark, and explicit user confirmation. Never infer a missing Before value from adjacent events.
